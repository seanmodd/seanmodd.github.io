Code ownership

Exactly what each person owns

Review is shared. Implementation authority is not.

Owner 1

Sean · Neon and web-app domain

Sean may change

  • Neon projects, branches, roles, grants, backups, and recovery settings
  • Existing web-app tables and their migration or bootstrap definitions
  • Conversation, ownership, share, star, usage, and budget persistence
  • The web half of the web-to-MCP contract
  • Web database guards, tests, and monitoring

Sean must not change

  • Kouhei's Drizzle schema source or migration history except through review feedback
  • MCP tools, Temporal orchestration, or Render deployment code
  • MCP runtime table definitions inside the web-app migration system
Owner 2

Kouhei · MCP and Drizzle domain

Kouhei may change

  • MCP tools, execution rules, Temporal integration, and safe API contracts
  • Drizzle schema and migrations for approved mcp_runtime.* tables only
  • Render configuration, health checks, canaries, and pooled Neon connection
  • MCP idempotency, workflow references, safe audit metadata, and migration scripts
  • Render database export, freeze, migration, and retirement

Kouhei must not change

  • Existing public.ai_*, mcp_ai_usage, CMS, account, or customer tables
  • Web-app database bootstrap or migration files
  • Neon roles, branches, recovery settings, or production administration
  • Customer-facing history, ownership, shares, stars, or budget records from the MCP

Handoff protocol

How work crosses the boundary

No owner edits the other owner's files to unblock themselves.

Handoff 01

Requirement

The requesting owner states the data shape, failure behavior, and acceptance test without prescribing changes inside the other repository.

Handoff 02

Owner implementation

The receiving owner implements inside their repository and database boundary, then publishes contracts or DDL for review.

Handoff 03

Independent review

The other owner reviews compatibility and boundary violations without taking direct edit authority.

Handoff 04

Contract test

Both repos test the same pinned contract version, request IDs, error categories, and idempotency rules.

Handoff 05

Rehearsal proof

The integrated system is proven on a Neon branch before production credentials or traffic change.

Handoff 06

Joint release gate

Sean approves Neon and web behavior. Kouhei approves MCP and Render behavior. Both must be green.

Non-negotiable guardrails

What must never happen

×No permanent dual-write between Render Postgres and Neon.
×No shared owner or superuser credential across Vercel, Render, and migration jobs.
×No drizzle-kit push against production.
×No MCP migration may alter a Sean-owned table.
×No web migration may mutate a Kouhei-owned runtime table.
×No secrets, raw database URLs, customer content, or tokens in reports.
×No raw prompts, addresses, or Senpex tokens in MCP runtime audit rows.
×No cutover before restore and negative permission tests pass.

Definition of done

Migration complete means the old database is gone.

Connecting the MCP to Neon is not enough. Duplicate authority, credentials, and write paths must be removed.

  • Neon is the only production Postgres platform for this AI system.
  • Sean-owned and Kouhei-owned tables are mechanically fenced.
  • Every product record has one canonical writer.
  • Render Postgres is exported and deleted.
  • PITR, export, and restore procedures are proven.
  • Runtime roles are least privilege and temporary credentials are rotated.
  • Grafana, Sentry, and database alerts cover the new path.
  • The ownership contract and runbook match production.
