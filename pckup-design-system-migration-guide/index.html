Pckup frontend modernization program

Migrate the existing codebase into a real, scalable design system.

This is not a redesign-from-scratch plan. It is an evidence-driven migration of a mature, production Next.js application with existing tokens, CI/CD, Figma assets, tests, and thousands of legacy styling decisions. The guide turns that complexity into 17 bounded phases with exact, copy-ready prompts.

Operating model

  1. 1Measure the system that exists
  2. 2Decide what should survive
  3. 3Build the canonical component layer
  4. 4Migrate one bounded surface at a time
  5. 5Delete legacy paths and enforce the new workflow

Current reality

Good token infrastructure, fragmented component architecture.

The existing token pipeline remains valuable. The migration closes the missing middle between tokens and product pages: canonical, reusable, testable components and shells.

Migration strategy

Strangler pattern, not replacement.

New canonical components are introduced beside legacy implementations, adopted through adapters and bounded route waves, then the old code is removed only after verified zero-use.

End state

Figma, code, tests, and delivery all share one contract.

Every production component has a typed code API, colocated styles, isolated examples, visual and behavior tests, a Figma counterpart, and a Code Connect mapping.

Target paradigm

The missing canonical layer

Pckup already has foundations and production pages. The migration creates the component platform between them, then moves every surface onto it.

Authority model

One owner for every type of truth

Bidirectional sync is useful only when authority is explicit. Circular ownership creates drift.

The workflow that replaces design drift

The final phase makes the new system the default path for every future interface change.
